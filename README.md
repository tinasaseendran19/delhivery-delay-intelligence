# Delhivery Last-Mile Delay Intelligence Pipeline

## Project overview

This project looks at shipment delays and uses the results to support delivery planning. It covers data cleaning, delivery-time prediction, delay prediction, grouping delivery hubs and suggesting actions for new shipments.

The project data is synthetic. It was created for this assignment and is not real Delhivery shipment data.

## How to run

Run the following commands from a fresh clone. These are the complete commands in the required execution order.

```text
git clone <your-repository-url>
cd delhivery-delay-pipeline
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

The scripts should be run in this order. `generate_data.py` creates the source data. Part A cleans it and creates the modelling table used by the later parts.

The `requirements.txt` file should pin the versions of pandas, NumPy, scikit-learn and joblib with `==`. The saved model, `models/delay_model.pkl`, is regenerated by running `python package_model.py`. A saved pickle depends on the scikit-learn version used to create it, so use the version pinned in `requirements.txt`. If the installed version is different, run `package_model.py` to create the model again.

## Data findings

The raw shipment file had 1,224 rows. After removing 24 duplicate rows, 1,200 shipments remained. The data had missing values in distance, parcel weight, declared value and payment mode. Five parcel weights were invalid scanner values and were treated as missing. Missing numeric values were filled using medians. Service type entries were standardised, leaving the three expected types: Express, Standard and Economy. After the hub details were joined, there were no missing values in the model features or target.

There were 278 delayed shipments out of 1,200, which is a delay rate of **23.17%**.

A few patterns were clear in the data:

- **Express** had the highest delay rate at **48.97%**. Standard was 20.56% and Economy was 8.57%.
- Delay rate increased with hub tier: **4.00%** for Tier 1, **21.50%** for Tier 2 and **44.00%** for Tier 3.
- Delay rate also increased with distance: **2.19%** for 0–200 km, **13.68%** for 201–400 km, **43.64%** for 401–600 km and **85.23%** for distances above 600 km.
- The three columns most strongly correlated with `delivery_hours` were `promised_hours` (**+0.8372**), `distance_km` (**+0.4013**) and `n_stops` (**+0.3247**).

The filled `declared_value_inr` column had a mean of **INR 1,533.05** and a median of **INR 1,121.50**. After taking the natural log, the mean and median were **7.0277** and **7.0224**. The log transformation brings the two values closer together and reduces the effect of very large declared values.

## Model results (regression)

The goal of this part was to estimate delivery time in hours. The data was split into 840 training rows, 180 validation rows and 180 test rows.

The mean baseline had a validation R² of **-0.021**. A negative R² means that predicting the training average was slightly worse than using the validation-set average.

Linear Regression had the lowest validation RMSE and was selected for the final test. Its validation RMSE was **4.89 hours**, with an R² of **0.931**. Gradient Boosting was very close, with a validation RMSE of **4.92 hours** and R² of **0.931**. The final Linear Regression model achieved a test R² of **0.949** and a test RMSE of about **4.52 hours**.

The decision tree results showed the difference between underfitting and overfitting. At depth 1, training RMSE was about **11.63** and validation RMSE was **12.13**, so both errors were high. This is a high-bias model. At depth 12 and with no depth limit, training error became much smaller while validation error stayed higher. The unlimited tree had training RMSE **0.00** and validation RMSE **7.84**, which is a sign of high variance.

For Gradient Boosting, learning rate **0.1** worked best, with validation R² of **0.931**. At **0.01**, learning was too slow for the 100 trees used and R² was **0.713**. At **1.0**, the model overshot and performance fell to R² **0.844**.

Cross-validation slightly favoured Gradient Boosting: its mean R² was about **0.935**, compared with **0.926** for Linear Regression. The validation RMSE was still lower for Linear Regression, so that is the model selected under the project's validation-based selection rule. The two results are close, so performance should be checked again with new data.

## Model results (classification)

This part predicts whether a shipment will miss its promised delivery time. The stratified split contained 840 training rows, 180 validation rows and 180 test rows. The training, validation and test sets had 195, 42 and 41 delayed shipments respectively.

The blind baseline had an accuracy of **76.67%**, but it predicted every shipment as on time. It therefore missed all 42 delayed shipments in the validation set. Accuracy on its own would give a misleading impression of the model.

The validation F1 scores for the first three classifiers were:

| Model | Validation F1 |
|---|---:|
| Logistic Regression | 0.8046 |
| Decision Tree (depth 6) | 0.7470 |
| Default Random Forest | 0.7848 |

The feature score results showed that the most useful seven features were `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag`. All five bookkeeping columns were outside the top seven by F-score. Together, those five columns contributed about **22.4%** of the Random Forest feature importance.

The feature-count comparison gave the following validation F1 scores:

| Number of features (K) | Validation F1 |
|---:|---:|
| 5 | 0.6988 |
| 7 | 0.8333 |
| 10 | 0.7857 |
| 12 | 0.8049 |
| 17 | 0.7848 |

Using seven features gave the best score in this comparison. Grid Search and Randomized Search did not improve the validation F1 over the default Random Forest with the same seven features. Their validation F1 scores were about **0.775** and **0.790**, compared with about **0.833** for the default forest. This is a useful reminder that tuning does not always improve results on a small validation set of 180 shipments. The final model therefore uses the default Random Forest with seven selected features.

The alert threshold was set to **0.5**. It was the highest tested threshold that kept validation recall at or above 0.80. At this threshold, validation precision was about **0.80** and recall was about **0.83**. Raising the threshold to 0.6 improved precision but reduced recall below 0.80. Since missing a delayed shipment is a bigger concern for this task, the 0.5 threshold was kept.

On the test set, the final model achieved:

| Metric | Test result |
|---|---:|
| Accuracy | 0.8667 |
| Precision | 0.6889 |
| Recall | 0.7561 |
| F1 score | 0.7209 |

Test recall was lower than validation recall. The test set had only **41 delayed shipments**, so a difference of a few predictions changes the recall noticeably. The final model settings are saved in `outputs/part_c_final_config.csv` and the test results are saved in `outputs/part_c_final_test.csv`.

## Operations recommendation

The 24 hubs were grouped into three operating segments based on their delivery performance.

| Segment | Number of hubs | Average delivery hours | Average delay rate |
|---|---:|---:|---:|
| Standard | 7 | 47.24 | 2.57% |
| Watch | 8 | 56.81 | 15.50% |
| Escalate | 9 | 64.65 | 46.00% |

The hubs in the **Escalate** segment and their delay rates are:

| Hub | City | Delay rate |
|---|---|---:|
| HUB13 | Nagpur | 46% |
| HUB15 | Kochi | 36% |
| HUB17 | Patna | 46% |
| HUB18 | Ranchi | 38% |
| HUB19 | Guwahati | 62% |
| HUB20 | Raipur | 48% |
| HUB21 | Bhubaneswar | 40% |
| HUB23 | Siliguri | 44% |
| HUB24 | Agartala | 54% |

These hubs should be reviewed first for route planning, staffing and capacity issues. Watch hubs should be monitored, while Standard hubs can continue with the usual process.

Four hubs did not match the segment normally expected from their tier:

- **HUB07, Kolkata:** Tier 1, but placed in Watch.
- **HUB13, Nagpur:** Tier 2, but placed in Escalate.
- **HUB15, Kochi:** Tier 2, but placed in Escalate.
- **HUB22, Dehradun:** Tier 3, but placed in Watch.

This shows that the tier label should not be used on its own to decide which hubs need attention. Actual delivery results should also be checked.

The alert threshold is **0.5**. On the test set, precision of 0.6889 means that about **6.9 out of every 10 flagged shipments** were actually delayed. Recall of 0.7561 means that about **7.6 out of every 10 delayed shipments** were identified by the model.

For the 48 new shipments, **8 were flagged**. Of those, **6** were assigned for hub-manager escalation and **2** for a proactive customer call. The remaining **40** required no action under the project rules.

Three segments were kept because the operations team needs three playbooks: Standard, Watch and Escalate. The separation ratio increased from **2.894** at K=2 to **5.393** at K=3. K=4 and K=5 had higher ratios, but their cluster sizes included groups with fewer than six hubs. Those smaller groups would be harder to manage as separate playbooks, so K=3 was retained.

## Production plan

Before using this in a live operation, I would connect it to regularly updated shipment data and review the results with the operations team. The project already has a few useful checks:

- **Accuracy:** `part_c_final_test.csv` records precision, recall and F1 on the held-out test set.
- **Reliability:** `part_d_reload_check.csv` checks that the saved model gives the same probabilities after it is loaded again.
- **Reproducibility:** the scripts use fixed random seeds, and the shipment scoring script produces the same CSV when run twice.
- **Maintainability:** data preparation, regression, classification, hub grouping, packaging and scoring are kept in separate scripts.
- **Consistency:** `clean_shipments()` and `build_features()` are shared between the historical data preparation and new-shipment scoring steps.
- **Monitorability:** the output CSV files make it possible to review hub segments, flagged shipments and model performance.

I would monitor these quantities each week and investigate when a trigger is reached:

- **Delay rate:** investigate if the weekly delayed share rises above **27%**, compared with the project's historical rate of 23.17%.
- **Flagged share:** review the model if the share of shipments flagged is below **10%** or above **25%** for several weeks.
- **Recall:** once delivery outcomes are known, review the model if recall falls below **0.70**.
- **Missing inputs:** investigate the data feed if more than **2%** of records have missing required feature values.

I would review performance monthly and retrain the model every three months, or earlier if delivery patterns change. The **15–28 September sale window** should be compared with other sale periods, not with ordinary weeks. The `sale_event_flag` should be kept because shipment volumes and delivery patterns can be different during a sale.

Possible data drift would include changes in delivery distance, number of stops, parcel weights, service type mix, hub capacity or the share of sale-period shipments. These changes could affect the predictions and should be checked before deciding whether to retrain.

## Limitations

- The data is synthetic, so it may not show all the problems found in a real delivery network.
- The test set contains only 41 delayed shipments. A few different predictions can change the reported recall and F1 score.
- The alert threshold was selected using one validation split. It should be checked again on new shipment data before being used for real operational decisions.
- The model uses the columns available in this dataset. Real delays can also be affected by live traffic, local weather, staffing changes and temporary hub disruptions that are not fully represented here.
